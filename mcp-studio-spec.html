Specification

MCP Studio

Your agents reach tools through MCP servers from several places: servers you connect by URL, servers from the MCP registry, local commands, and APIs that have an OpenAPI, GraphQL, or gRPC definition but no MCP server. MCP Studio adds a server from any of them, lists every tool it offers, and lets you import the tools agents may call, with a risk classification on each. Every server is stored the same way, in one folder in the steering repo, reviewed by steering PR, and served by the cloud gateway with the workspace's credentials, policies, and budgets.

Today

  • import_tools (tool.import.ts) publishes picked tools from a server's pinned snapshots into agent.tools and agent.tool_versions. An unclassified import lands as risk high and not read-only.
  • The classification vocabulary: risk grade low to critical, side effect read, write, or irreversible, egress local, org_tenant, or third_party, consequence tags (renamed impacts here), measures, and data classes (contracts/tool.classification.ts).
  • mcp.mcp_servers holds servers with transport streamable-http, sse, or stdio. mcp.tool_snapshots holds every descriptor a server returned. mcp.credentials holds secrets, envelope-encrypted with a KMS key.
  • No OpenAPI, GraphQL, or gRPC code exists. No customer agent receives a toolbelt yet.

Proposed

  • One folder per server, servers/<name>/, with server.toml, tools.toml, and tools.lock.json, whatever the source.
  • The repository decides what agents see. Oxagen's tables are rebuilt from it on publish and hold only what a repository cannot: secrets, discovery, health, the compiled form, and the off switch.
  • A lock file pins each imported tool's upstream definition, so a server cannot change what the model reads without a steering PR.
  • The agent sees annotations derived from the classification, not the ones the server sent.
  • Two exposure modes, direct and search, for any server.
  • A format-neutral operation model, so compile, checks, policy, sync, and serving treat every definition format the same.
Storage

Storage model

The repository decides which servers exist, which of their tools agents can see, and how each tool is classified and shaped. Oxagen's tables hold what a repository cannot: secrets, what each server offers, health, the compiled form, and the off switch. Publish rewrites the registry rows from the merged files, so a row never disagrees with the repository. Proposed

Server folder

Every server has the same three files. A server built from a definition adds it: openapi.yaml, schema.graphql, or proto/. Any server can add tests.

The folder name is the server name and the prefix of every tool name. The repository grows with the tools you import, never with the size of the server: a GitHub server that offers 90 tools with 6 imported holds 6 entries.

Publish

  1. Compile.

    Each changed server folder compiles to effective tool definitions: the locked upstream definition with tools.toml applied.

  2. Upsert the server.

    One mcp.mcp_servers row per folder, keyed by workspace and name, with origin = 'steering'.

  3. Upsert the tools.

    One agent.tools row per imported tool, slug <server>__<tool>. A new definition hash writes a new agent.tool_versions row through publishTool, and active_version_id moves to it.

  4. Write the classification.

    The classification columns take the values in tools.toml. A change there bumps the deny generation, as a reclassification does today, so the gateway reloads it.

  5. Retire.

    A tool removed from tools.toml is disabled and keeps its rows for replay. A removed folder soft-deletes its server, which keeps its snapshots for 365 days, as today.

  6. Bundle.

    The tool manifest joins the published version.

The in-app agent. Rows with origin = 'steering' reach wrapped agents only. The in-app agent's tool reader (packages/agent/src/runtime/materialize-tools.ts) skips them. Decided for the rule, Proposed for the column.

Suggestions

Studio fills in a suggestion for each imported tool. A person confirms or changes it before the steering PR opens, and a tool without risk, side_effect, and egress fails the schema check. A server's annotations are its author's hints. The MCP specification tells clients to treat them as untrusted, so Studio never applies one without a person.

SignalSide effectRiskImpacts
readOnlyHint: true, GET and HEAD, a GraphQL query, or a gRPC method marked NO_SIDE_EFFECTSreadlow

destructiveHint: true, or DELETEirreversiblehighdestroys_data

Egress is suggested from how the server is reached: local for a local command, org_tenant through a relay or when openWorldHint is false, and third_party otherwise.

Rules

  • The agent sees Oxagen's annotations. The gateway sends annotations derived from the classification: readOnlyHint for read, destructiveHint for irreversible, and openWorldHint for third_party. A harness's own approval prompt then matches Oxagen's view of the tool, whatever the server claimed.
  • Classification is outside the tool version. The version hash covers what the model reads: name, description, and input and output schemas. Changing a tool's risk is a steering PR and never a new tool version, as reclassifying never changes a checksum today.
  • Policies read it. Cedar sees context.tool.risk, side_effect, and egress (agent policy spec), so a rule such as irreversible.approval covers every imported tool with no rule written per tool.
  • Reviewers see it. The steering PR lists every tool whose classification changed, and governance.toml can route servers/** to a reviewer group.

impacts joins the agent policy spec's Tool type and replaces its financial_class, so Cedar, the repository, and the code share one vocabulary. The policy spec's egress values move to the code's as well. Issue #141 tracks that page.

Lock file

Lock file

A server can change a tool's description or schema at any time, and a changed description is an instruction the model will read. tools.lock.json pins the upstream definition of every imported tool as it was when a person reviewed it. The gateway serves only locked definitions, so what the model reads changes only through a steering PR. Proposed

  • Written by Oxagen only. Studio writes it into the steering PR it opens. When a person edits tools.toml by hand, the stamp commit recomputes definition_hash and version. The owned check refuses a hand edit.
  • Upstream moves only in a sync PR. Oxagen replaces a tool's upstream only in a pull request that shows the change.
  • Every source has one. For a server built from a definition, upstream is the tool compiled from it before tools.toml applies, so a definition change shows as a change per tool instead of a long schema diff.
  • Local servers pin the code. For a local server the lock also records the resolved package: name, version, and a digest of the package or binary. The local gateway refuses to start a command whose digest does not match, so the review covers the code that runs, not only its name.
  • Diffs stay readable. Keys are sorted and indented two spaces, so a pull request shows each changed field on its own line. Limit 5 MB.
  • Hashes. upstream_hash is SHA-256 over the RFC 8785 canonical form of upstream, as record hashes are computed. definition_hash covers the effective name, description, and schemas, and version rises by one when it changes.

Local servers

The cloud gateway decides every call to a local server, so there is one policy engine, the off switch stays instant, and every governed action is recorded. The cost is one round trip per call, small beside a model call. Decided

  • Machines. An admin puts enrolled machines into named groups in Oxagen. A machine runs a local server only when its group is in source.machines.
  • Pinned code. The lock records the package's name, version, and digest. The local gateway refuses to start anything else.
  • Signed calls. The local gateway runs a call only on an envelope the cloud gateway signed, bound to the tool version, a hash of the arguments, a nonce, and an expiry a few seconds out. It keeps no cached decisions and no policy engine of its own, and it fails closed when it cannot reach the cloud gateway.
  • Results. A result passes the local gateway's sensitive-data screen, then returns through the cloud gateway, so shaping, redaction, the record, and metering each have one implementation.
  • Discovery. A machine in the group reports tools/list, and the sync PR names the machine that reported.
  • No offline mode. If one is ever needed, it can come later as short-lived signed grants for read-only tools.

Definition import

  • OpenAPI. OpenAPI 3.1 and 3.0 in YAML or JSON. Swagger 2.0 is converted to 3.0 at compile time, and the original stays in the folder so a sync diff compares like with like.
  • Many files. A document split across files with external $refs is bundled into one file on import.
  • Normalize at compile, never in the file. Resolve $ref, merge path-level and operation-level parameters, turn 3.0 nullable into 3.1 type lists, and apply overlay.yaml when it exists.
  • GraphQL. An SDL file, or an introspection query through the network route. Production servers often turn introspection off, so a file in a linked repository is the usual source.
  • gRPC. The .proto files with their imports, or server reflection. Oxagen writes what reflection returns to proto/ as .proto text, so a person can review it.
  • Refused. Definitions over 25 MB. OpenAPI webhooks and callbacks, GraphQL subscriptions, and gRPC client and bidirectional streams are listed but never become tools.

Names

Tool names

A tool's full name is <server>__<tool>, as the agent policy spec writes stripe__create_refund, for every source. The server name matches ^[a-z][a-z0-9_]{0,23}$, the tool name ^[a-z][a-z0-9_]*$, and the whole name stays within 64 characters, the limit model APIs set on tool names. An upstream name that breaks the rule, such as get-issue, is imported under a key that keeps it (get_issue) with upstream = "get-issue". Two tools with one name fail the compile check. A pinned reference adds the version: billing__create_refund@3. A toolbelt may list billing__* to grant every imported tool of a server. Proposed

Large servers

Large servers

An enterprise API can hold 1,500 operations, and some MCP servers offer over 100 tools. At about 250 tokens a definition, 1,500 tools would cost 375,000 tokens on every model request. Every server has one of two exposure modes. Proposed

ModeThe agent seesFitsDefinition cost per request
directOne tool per imported toolUp to about 40 tools, or whatever fits definition_budgetThe sum of the definitions, shown in Studio before the steering PR opens
searchThree tools: <server>__search returns up to 10 imported tools as one line each, <server>__describe returns one tool's input schema, and <server>__call runs itAny sizeAbout 900 tokens, plus what the agent looks up
  • Policy sees the real tool. The gateway decides billing__call with tool: "create_refund" as billing__create_refund. Cedar rules, toolbelt grants, classification, approvals, and spend attribution work the same in both modes.
  • Search shows only what the agent may call. Visibility is permission, so a search never returns a tool outside the agent's toolbelt.
  • The tool list never changes mid-session. A fixed list keeps the provider's prompt cache warm. Tool lists that grow during a session break the cache and depend on each harness handling list changes.
  • Ranking. search ranks with embeddings of each tool's one-line entry. By default Oxagen embeds with Voyage AI's voyage-4-large on its own shared key and absorbs the cost. A workspace can set its own embedding endpoint, model, and key, or decline embeddings and rank by keyword. Decided
  • Only changes are embedded. Publish embeds entries whose content hash changed, through a queue that batches them, so one large import cannot use up a shared rate limit. When the endpoint fails, search falls back to keyword matching.
  • Studio recommends a mode. When the imported definitions pass definition_budget, Studio suggests search. The names search, describe, and call are reserved in a server that uses it.

Mutual TLS, common on gRPC services and named mutualTLS in OpenAPI, runs through a relay, which keeps the client certificate inside the customer's network. Signed requests such as AWS SigV4 come later. When an operator has not connected an account, the call returns isError with "Connect your Billing API account in Oxagen, then retry," and the link.

Network paths

Oxagen can stop an agent only while the agent has no credential it could use without the gateway. A credential on the agent's machine could be read and used directly, so private networks are reached through the relay instead. Decided

Relay rules

These rules make the relay a hard stop: when the cloud gateway stops signing, nothing can make the relay act.

  • Signed envelopes. Each envelope carries the cloud gateway's signature, an expiry a few seconds out, a nonce, and the exact method, host, and path, or the exact gRPC service and method.
  • Refusals. The relay refuses an envelope that is unsigned, expired, replayed, or aimed at a host its local allowlist does not name.
  • Fails closed. When the connection to Oxagen drops, the relay sends nothing until it reconnects.
  • Protocols. HTTP/1.1, HTTP/2 including gRPC, and MCP streamable HTTP.

Relay placement

Run the relay on infrastructure the agent cannot reach, such as a cluster or a VM. For a small setup on one machine, run it as a separate OS user or container with its own secret store. That is weaker, but the agent process still has no direct path to the credential.

Relay packaging

The relay ships as a container image and as a Helm chart that deploys it. Decided

Customer-held credentials

A customer that will not give Oxagen a credential can keep it in the relay, which adds it to the request after checking the envelope. This needs the Enterprise plan and some setup, and the website advertises it as an Enterprise feature. Every other plan uses a credential in Oxagen's vault. Decided

Host rules

  • Fixed hosts. Hosts come from the reviewed server.toml. Path parameters are percent-encoded. A redirect to another host is refused.
  • No private addresses from the cloud. The cloud route refuses private, loopback, and link-local addresses. A private server goes through a relay.
Runtime

Call path

One path for every source. Only the send step differs. Proposed

  1. Receive.

    The agent calls billing__create_refund. The call passes the local gateway, then reaches the cloud gateway.

  2. Find.

    The tool at its locked version in the published bundle. A tool that is off, withheld, or outside the agent's toolbelt is refused.

  3. Validate.

    The arguments against the effective input schema. Bad arguments return isError with the schema error.

  4. Decide.

    Toolbelt grant, Cedar rules with the tool's classification, and budget. An approval parks the call and asks the operator.

  5. Shape the input.

    Fixed values and defaults added, renamed inputs mapped back to the upstream names.

  6. Authenticate.

    The credential from the vault for the agent's environment, or the operator's token.

  7. Send.

    An MCP source receives tools/call with the upstream name. An OpenAPI source receives the HTTP request built from the operation, with an idempotency key where configured. A GraphQL source receives one POST with the stored selection set and the arguments as variables. A gRPC source receives the call from a client that encodes and decodes from the descriptors, with no generated code. A local source runs on the agent's machine when the local gateway receives the signed envelope, and its result returns through the cloud gateway. Every send has a 30-second deadline by default.

  8. Retry.

    OpenAPI GET, HEAD, PUT, DELETE, and a POST with an idempotency key retry on 429, 502, 503, and 504, up to 3 times. A GraphQL query retries as a GET does, and a mutation never retries. A gRPC call retries on UNAVAILABLE only when its method is marked NO_SIDE_EFFECTS or IDEMPOTENT. An MCP call retries only when the transport failed before the server received it.

  9. Shape the result.

    select, redact, and the size cap, then structuredContent and text.

  10. Record.

    The decision, status, latency, bytes, and the arguments and result as the workspace's retention setting allows. Meter the call as a governed action.

Sync

Sync

Discovery runs on the server's schedule, on an MCP server's notifications/tools/list_changed, and on a push that changes a definition in a linked repository. GraphQL introspection and gRPC reflection run on the schedule. It writes every tool it sees to mcp.tool_snapshots. When an imported tool's upstream definition differs from the lock, Oxagen opens one sync PR for the server with the new lock and a tool surface diff. New tools are listed and left unimported. A changed input schema is marked breaking, and the tool stays withheld until the PR merges. Proposed

A registry server's new version is a sync PR that changes source.version and the lock together.

Testing

Try it and tests

  • Try it. Call any imported tool from Studio in an environment, with your own credential and under the same policy an agent meets. Studio shows what went upstream, the raw result, and the shaped result the model would receive.
  • Save as a test. One click writes the call to tests/calls.jsonl: the arguments, the recorded response, and the shaped result.
  • Replay in the PR. The compile check replays every recorded call with no network: the shaped result must match, and for a server built from a definition the built request must match too.

Spend

The spend ledger charges each server for what it adds to a request: its tool definitions on every request that carries them, and its results on the requests that follow a call. Every use of Oxagen to steer, govern, or provide a tool is a governed action. Each tool call, each search and describe call in search mode, and each Try it call is metered as one. Decided The rule covers every call Oxagen gates, so a call that policy denies or parks for approval counts too.

With the default endpoint, embedding search entries costs Oxagen the Voyage AI price of the changed entries on each publish. Summary

Where Oxagen leads

  • Runs: a live view, operator control, and a kill switch per run. Kong controls requests, not runs.
  • Spend per run, work item, and agent, including waste. Kong attributes cost per consumer and model.
  • Tool classification, approvals, and pinned definitions. Kong has hints with no policy, and no pinning.
  • Steering, skills, and memories delivered to your agents. Kong delivers only its own skills.
  • A local gateway on the developer's machine. Kong asks for a base-URL change.

Where Kong leads

  • A shipping model gateway: routing, failover, key custody, and caching.
  • Content safety: PII redaction, prompt guards, and six content safety services.
  • Shipping MCP controls: OAuth 2.1, per-tool ACLs, and OpenAPI to MCP.
  • Policy engines that run today (OPA, CEL), where Oxagen's Cedar evaluator is not built.
  • Deployment choices and certifications for regulated buyers.

Improvements

Where Oxagen can improve

  1. Ship the cloud gateway's model path.

    Provider keys, routing, and failover. Oxagen's run control and spend depend on it, and Kong ships it today.

  2. Enforce budgets before the call.

    Kong applies cost limits one request late. Checking before the call is a lead Oxagen can take.

  3. Ship MCP Studio's serving path.

    Proxying, operator OAuth, and toolbelts for customer agents close Kong's MCP lead.

  4. Land the Cedar evaluator.

    Classification and approvals mean nothing until a policy engine reads them.

  5. Ship the on-device screen.

    Screening before data leaves the machine beats redaction at a remote gateway, once it exists.

  6. Call content safety services.

    Buyers already pay for Azure, AWS, or Lakera services and will ask for them.

  7. Offer a customer-hosted gateway.

    Kong's AI Gateway 2.x needs Konnect, which leaves an opening for regulated buyers.

  8. Export OpenTelemetry.

    Buyers expect runs and tool calls in the tools they already watch.

  9. Start SOC 2 Type II.

    Kong's certifications clear procurement that Oxagen cannot clear yet.
