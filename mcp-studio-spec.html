Specification

MCP Studio

An agent can call an HTTP API, but first it has to find the endpoint, read the docs, build the request, and hold a key. An MCP server hands the model a named tool with a typed input and a one-line description, so it picks the right call and fills it in correctly. MCP Studio turns an OpenAPI document into that server. You choose the operations, Oxagen writes the tools, a steering PR reviews them, and the cloud gateway serves them with the workspace's credentials, policies, and budgets.

Flow

How it works

No code is generated and nothing is deployed. The cloud gateway interprets the published tool manifest, so a merged steering PR is live in seconds. Proposed

1 ImportFetch the documentUpload, URL, or a path in a linked code repository
2 NormalizeOne clean documentResolve references, merge parameters, convert Swagger 2.0
3 CurateChoose and shape toolsNames, descriptions, hidden fields, response size, risk
4 ReviewOpen a steering PRThe tool surface diff and every check in one place
5 PublishMergeThe tools join the workspace's published version
6 ServeThe cloud gatewayOne MCP endpoint every harness already points at
7 CallThe APIPolicy, credential, request, shaped result, record
Decisions

Decision status

Decided

  • Configuration and steering changes are reviewed in pull requests. MCP Studio writes to the steering repo through steering PRs. (Mac, 2026-09-26)
  • Oxagen creates the steering repo, which holds tools as well as steering. (Mac, 2026-09-26)
  • The cloud gateway holds the vendor keys and MCP credentials. No MCP credential sits on an enrolled machine. (Mac, 2026-09-25, ADR-187)
  • Oxagen bills governed actions only. The customer pays the model provider on its own key. (Mac, 2026-09-25)

Today

  • MCP tables exist: mcp.mcp_servers, mcp.credentials (envelope-encrypted with a KMS key), and mcp.tool_snapshots (packages/database/src/schema/mcp.ts).
  • apps/mcp serves Oxagen's own capability contracts. No customer agent receives a toolbelt yet.
  • No OpenAPI parsing exists. The unbuilt v2 contract register-tool-server.ts names an openapi transport.
  • No Cedar evaluator exists. Decision rules run in packages/rules.

Proposed

  • The folder apis/<name>/ with api.toml, the vendored document, and tools.toml.
  • An interpreter in the cloud gateway, not generated code.
  • Two exposure modes: direct and catalog.
  • A relay for APIs inside a private network.
  • Operator OAuth, so an API's own permissions apply to the person who runs the agent.
  • A Studio tool call counts as a governed action.
Files

Files in the steering repo

One folder per server under apis/. Names follow the steering repo's Shared contract. Proposed

An operation absent from tools.toml is not a tool. A key is the operation's operationId, or "POST /refunds/{id}/cancel" in quotes when the operation has none. The file grows with the tools you expose, never with the size of the API.

Names

Tool names

A tool's full name is <server>__<tool>, as the agent policy spec writes stripe__create_refund. The server name matches ^[a-z][a-z0-9_]{0,23}$, the tool name ^[a-z][a-z0-9_]*$, and the whole name stays within 64 characters, the limit model APIs set on tool names. billing__ leaves 55 characters for the tool. Two operations that map to one name fail the compile check. A pinned reference adds the version: billing__create_refund@3. Proposed

Large APIs

Large APIs

An enterprise API can hold 1,500 operations. At about 250 tokens a definition, listing them all would cost 375,000 tokens on every model request. Studio offers two exposure modes. Proposed

ModeThe agent seesFitsDefinition cost per request
directOne tool per selected operationUp to about 40 tools, or whatever fits definition_budgetThe sum of the definitions, shown in Studio before publish
catalogThree tools: billing__search returns up to 10 operations as one line each, billing__describe returns one operation's input schema, and billing__call runs itAny sizeAbout 900 tokens, plus what the agent looks up
  • Policy sees the real operation. The gateway evaluates billing__call with operation: "createRefund" as billing__create_refund. Cedar rules, toolbelt grants, approvals, and spend attribution work the same in both modes.
  • Search shows only what the agent may call. Visibility is permission, so billing__search never returns an operation outside the agent's toolbelt.
  • The tool list never changes mid-session. A fixed list keeps the provider's prompt cache warm. Tool lists that grow during a session break the cache and depend on each harness handling list changes.
  • Studio recommends a mode. When the selected definitions pass definition_budget, Studio suggests catalog.

A customer that will not give Oxagen a credential can keep it in the relay, which adds it to the request. Proposed

  • Fixed hosts. The base URL comes from api.toml and was reviewed. Path parameters are percent-encoded. A redirect to another host is refused.
  • No private addresses from the cloud. The cloud route refuses private, loopback, and link-local addresses. A private API goes through a relay.
Risk

Risk and policy

Every Studio tool enters Cedar with the same facts as any other tool: context.tool.name, context.tool.risk, context.tool.server, context.tool.method, context.tool.path, and context.args. The agent policy spec's rules, such as irreversible.approval, apply with no extra writing. The toolbelt grant compiles from each agent's tools list, where billing__* grants every tool of the server. Proposed

risk defaults from the method. Only a person sets irreversible, because the document cannot say whether money moved or a message was sent.

Runtime

Call path

  1. Receive.

    The agent calls billing__create_refund. The call passes the local gateway, then reaches the cloud gateway.

  2. Validate.

    The gateway finds the tool in the published version and checks the arguments against its input schema. Bad arguments return isError with the schema error.

  3. Decide.

    Toolbelt grant, Cedar rules, and budget. An approval parks the call and asks the operator.

  4. Build.

    The base URL for the agent's environment, then the path, query, headers, and body, with fixed values and an idempotency key for a POST that has one.

  5. Authenticate.

    The gateway adds the credential from the vault, or the operator's token.

  6. Send.

    Directly or through the relay, with a 30-second timeout by default.

  7. Retry.

    GET, HEAD, PUT, DELETE, and a POST with an idempotency key retry on 429, 502, 503, and 504, up to 3 times, after the Retry-After the API sends. Any other POST never retries.

  8. Shape.

    Apply select, redact, and max_response_bytes, then return structuredContent and text.

  9. Record.

    The decision, status, latency, bytes, and the arguments and result as the workspace's retention setting allows. Meter the call as a governed action.

Versions

Versions and sync

A tool's version rises by one when its compiled definition changes: name, description, schemas, annotations, or risk. A published version pins every tool's version, and a Cedar rule can hold one, as the agent policy spec's held tool version does. Proposed

When the source document changes, Oxagen compiles the old and the new, compares the tool surfaces, and opens a steering PR on apis/billing with the new document and the diff. A new operation is listed and left unselected. A breaking change is marked, and the tool keeps its old version until the PR merges.

Testing

Try it and tests

  • Try it. Call a tool from Studio against an environment, sandbox by default, with your own credential and under the same policy an agent meets. Studio shows the HTTP request, the raw response, and the shaped result the model would receive.
  • Save as a test. One click writes the call to tests/calls.jsonl: the arguments, the recorded response, and the shaped result.
  • Replay in the PR. The compile check replays every recorded call against the compiled tool with no network: the built request and the shaped result must match. Tools with no recorded call get a response generated from their schema.
  • Selection tests. Each line of tests/selection.jsonl holds a task and the tool that fits it. On request, Studio asks a model on the workspace's route to pick from the server's tools and reports how often it picked right. It never runs on its own, because it spends model tokens.

Proposed

Spend

Spend

The spend ledger charges each server for what it adds to a request: its tool definitions on every request that carries them, and its results on the requests that follow a call. Studio shows the definition cost before publish and each tool's average result size from real calls after. A server whose tools are on and never called shows that cost plainly. Proposed

Agent feedback

Two signals show where a tool confuses agents. A reflection's tool_feedback names the tool and the problem (steering repo spec, Memory and reflection). Open questions

Open questions

  1. Whether a Studio tool call counts as a governed action for billing.
  2. Drafting descriptions with the in-app agent: billed as in-app agent spend, on the Billing page.
  3. The relay's packaging: a container image, a Helm chart, or both.
  4. Catalog search by keyword, or by embeddings at a small cost per publish.
  5. Customer-held credentials in the relay, for every plan or for the largest customers only.
