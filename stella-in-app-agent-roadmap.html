You ask stella a question from any workspace page, and today it reads the record and answers in up to 12 steps with no shell, no files, and no way to make a chart or stage a change. stella in the terminal plans, runs code, edits files, delegates to children, and works for hours. This spec closes that gap inside the capability roadmap's four abilities (understand, make sense, make, act), and every effect still passes Oxagen's gates.

01

Overview

What the in-app agent becomes, and the rules it keeps.

Target

stella in the app does what stella in the terminal does, plus what the capability roadmap asks for that the terminal lacks: evidence-linked answers, deterministic charts, durable artifacts, action plans applied by digest, and distribution with receipts.

Parity definition

A 30-task bench (S05) runs each task through both agents on the same model. The in-app verdict rate lands within 5 points of the terminal's, and steps and cost land within 1.25 times. Pass rate alone saturates, so steps, cost, and interventions are scored too.

Source of the sandbox

Neither source document asks for a sandbox. It comes from the parity goal and from the maintainer's decision on 2026-09-25 that stella gets contained sessions. Section 04 has the design, and D1 records it as an ADR.

Rules that hold in every phase

  • The engine holds no authority. stella-serve never calls a model or runs a tool. STELLA_SERVE_TOOLS accepts only remote (crates/stella-serve/README.md). Every model call and tool call comes back to Oxagen.
  • Every effect is a contract. A file write, a shell command, a chart render, and a pull request each run through kernel.invoke() with IAM, entitlement, approval, and metering, and each leaves a frame on the turn's run.
  • No runtime grows back. ADR-043 deleted Oxagen's sandbox, sub-agent, web, and artifact packages because Stella owns them. The tools here are Stella's own code, and sub-agents run inside the engine. Oxagen adds gates, a driver, and stores.
  • No key enters the agent. A GitHub installation token never enters the engine or the sandbox (ADR-151). Clones come through a short-lived archive URL or a host proxy, and commits are written host-side.
  • Any agent can call the new families. Oxagen governs Claude Code and Codex too. Each new family ships on the agent, api, and mcp surfaces, so stella is the first caller and not the only one.
  • AWS only. Nothing on the path depends on Vercel, and the app host has no Docker. Production artifact storage moves off the Vercel Blob driver in @oxagen/storage.

04

Containment

How a stella session earns the contained tier.

contained is the top of the tier ladder (ADR-095: observe, harness, gateway, contained) and the only tier that earns "enforced" against the machine's operator. It is built for Claude Code and Codex as tacho run --contained with the Docker profile oxagen-linux-docker-v1 (ADR-152, packages/tacho/src/contained/). A sandbox alone does not earn it. ADR-096 requires three controls, and the control plane computes the tier from a launch receipt and the run's record. A launcher never labels its own run. ADR-095 counts gateway traffic in that record, and a stella session sends none because the engine runs outside it. D1 therefore adds a rule for arun_ runs: a receipt naming all three controls, plus a frame for every tool call showing it entered through the host.

1Egress

Customer harness: every model and MCP request goes through the gateway or fails. stella session: nothing leaves the microVM. The engine runs outside it, so there is no model route and no MCP route. The one channel is the tool host's socket to Oxagen. A repository arrives as an archive the host fetched.

2Filesystem policy

Customer harness: the workspace is writable and the hook config is read-only. stella session: the session workspace is the only writable path. The tool host binary and its config are read-only, and no credential file enters.

3Integrity at launch

Customer harness: a digest of the hook configuration is recorded. stella session: the image digest and the tool host digest are recorded on a launch receipt before the first tool call, the way register_contained_launch records one today.

Why a stella session is stricter than a wrapped harness

In a wrapped harness the agent's own tools run inside the sandbox, so a hook is the only thing that can refuse them. ADR-096 pins the hooks read-only to close that gap. stella's tools never run on their own. The engine asks, Oxagen gates the call through kernel.invoke(), and only then does Oxagen send it into the session. Refusal happens before the sandbox sees anything. The sandbox then bounds what an allowed call can reach.

Limits. ADR-152 states what the tier does not cover, and the stella profile inherits the same limits. Enforcement holds against the agent and every process it starts, not against whoever administers the host. For stella that administrator is Oxagen's own operations. The receipt is a launcher attestation with no hardware signature. A microVM holds against a stronger escape than a container does. Neither boundary changes what a host administrator can do.

Architecture

The target shape of one turn.

turn to the enginetool trafficgates and evidenceperson

The engine never touches the contained session. It asks for a tool, Oxagen gates the call, and only an allowed call is forwarded. The seams the capability spec names map onto this picture: the capability gateway is the gates box, the context service is Workspace Context, and the analysis, visualization, artifact, action, and distribution runtimes are the family boxes.

Decisions

Four ADRs gate the build, and five smaller choices ride the spec that needs them.

D1Phase 0
Contained sessions for stella

Decided on 2026-09-25: stella gets a sandbox. The ADR amends ADR-043 Decision 2, ADR-053 section 1, and docs/VISION.md drift test 6, adds the tier rule for arun_ runs to ADR-095, and records the profile. Recommendation: an ECS task on Fargate per thread for the first profile, since it gives each session its own kernel with no metal fleet to run. Firecracker on metal hosts is the second profile if start time or cost demands it. Refs #4176.

D2Phase 0
Sub-agents and long turns

stella-serve runs read-only children under operator caps and holds sessions with checkpoints. ADR-043 retired Oxagen's own fan-out (ADR-010). The ADR sets the caps (children per turn, steps per child, steps per turn kind, wall time), how child calls bill and record, and how a turn outlives the flyout under ADR-092.

D3Phase 0
Workspace Context names

The capability spec proposes query_context and get_context_entity. Oxagen's context.* family already means steering records, and ADR-137 calls standing decisions "workspace context records". Recommendation: a workspace_context.* family with agent names such as query_workspace_context, and search_graph plus the ontology tools kept as aliases for one migration cycle.

D4Phase 2
Where analysis runs

Open decision 2 of the capability spec. Recommendation: both, in sequence. A governed read writes a snapshot with its provenance into the contained session, and analysis code runs over snapshots only. The session never queries a live store.

Workflows

How each prompt uses Claude Code's Workflow tool.

Every prompt opens with "Use a workflow for this", which is the opt-in the Workflow tool requires, and states how many agents it runs so a small default does not cap it. It then carries a complete script to pass inline as script. The same script runs one spec or many: the composed prompt puts every selected spec in one pipeline(), so each spec moves through the stages on its own clock.

  1. Confirm

    Two or three read-only agents check the spec against current main: paths, issue state, and whether each dependency has merged. Any blocker stops that spec before a line is written.

    parallel, schema MAP
  2. Design

    One agent turns the facts into a plan: one unit per commit, with files and tests. For a decision it lays out the options for the ADR.

    one agent, schema PLAN
  3. Build

    One agent per unit, in order, on one branch in one worktree under ~/Projects/.worktrees/. Each commits before the next starts, so no two agents edit the same tree.

    sequential, schema BUILT
  4. Verify

    Three agents try to show the branch misses its done list, each through one lens: correctness, governance, or completeness. A finding needs a file, a line, and a failing scenario.

    parallel, schema FINDINGS
  5. Fix

    One agent reproduces each finding, skips any it cannot, and fixes the rest with a test that fails first.

    one agent

The workflow never pushes. When it returns, the session reads the result, pushes each finished branch, opens its PR (a draft for a decision), and starts the watcher the global CLAUDE.md requires. A spec that stopped is reported with its blockers and gets no PR.
