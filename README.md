# Oxagen Mission Control — mockups

Every mockup is a single self-contained HTML file. Open it in a browser, or serve
the folder (`python3 -m http.server`) and browse to it. Each file carries its own
mockup chrome (states, phone width, theme) in the corner; that chrome is not product UI.

The demo record is the same everywhere: Anderson Intelligence Corp. (`a-intel`), workspace
`core-platform`, operator Marcus Bell.

## The showboat

| File | What it is |
|---|---|
| `mc.html` | **The Ten Pages.** The final design: every page of Mission Control, everything W1–W11 and W13 showed ported into it, the onboarding flow, and the twelve W flows as guided scenarios. The single source for the app build and for w1–w11 and w13. Start here. |
| `consolidated.html` | **The product build of `mc.html`**: every page, dialog and auth screen, with the mockup chrome taken off (no state bar, no scenario rail, no onboarding-demo entry points). Lays itself out for a phone when the viewport is one. Generated by `tools/build-pages.mjs`; do not edit. |
| `consolidated-loaded.html` | The same, pinned to the loaded state and the desktop shell. The file to open for the desktop design. |
| `consolidated-loaded-mobile.html` | The same, pinned to the loaded state and the mobile shell: a five-slot thumb bar (Fleet · Agents · Tools · Spend · More), a More sheet with the rest of the app, dialogs as bottom sheets, list tables as labelled cards, 44 px targets, safe-area insets. The file to open for the mobile design. |
| `pages/` | One file per page per state (loaded, empty, loading, error, denied), desktop and mobile — 250 files — plus, beside each page, `<page>.md` (its data sources and functionality) and `<page>.audit-prompt.md` (a prompt that audits a build of that page against the spec). `pages/index.html` is the map; `pages/audit-prompt.md` audits the whole app. See `pages/README.md`. |

### Onboarding inside `mc.html`

The W1 pre-app screens live in `mc.html` at `#/welcome…` and are reachable three ways:

- **Account dialog → Onboarding tab** (avatar in the sidebar → Account → Onboarding): every step with an Open button, and "Start from sign-up".
- **User menu → Onboarding demo.**
- **⌘K → "Onboarding demo — sign up" / "— log in".**

The path is sign up → verify email → name the organization → wrap an agent → start a run.
The gate steps reuse the Register Agent components Fleet already uses, so the wrap
and first-frame panels are the same code. Log in, two-factor, forgot/reset password
and accept-invitation are in the set too. "Exit demo" on any screen returns to Fleet.
Nothing on these screens writes anything; it is clickable demo chrome and is not
meant to ship in the live app.

## One flow per file (W1–W13)

**W1–W11 and W13 are generated from `mc.html`. Do not edit them.** Each one is `mc.html` byte for byte
except its `<title>` and the hash it opens on: its guided scenario, a rail of four to eight
steps over the real screens (`#/a-intel/<workspace>/scenarios/<id>/<step>`). A scenario owns no
screens, so a W file cannot drift from the design it demonstrates. To change what a W file
shows, change `mc.html` (the page, or the flow's `SCENARIOS["id"]` entry) and rebuild:

```sh
node tools/build-w.mjs            # regenerate w1–w11 and w13 from mc.html
node tools/build-w.mjs --check    # exit 1 if any W file is not exactly what mc.html produces
node tools/check-scenarios.mjs    # walk every step of every scenario in Chromium
node tools/baseline/check-baseline.mjs mc.html
node tools/build-pages.mjs        # regenerate consolidated*.html and pages/ from mc.html
node tools/build-pages.mjs --check
node tools/check-pages.mjs        # open every generated page file in Chromium and check it
```

The same goes for the product files: **`consolidated*.html` and `pages/*.html` are generated
from `mc.html`. Do not edit them.** A generated file differs from `mc.html` in four places only —
`PRODUCT` is true (which hides the state bar, the scenario rail and nav item, and the onboarding
demo's entry points and "Exit demo" buttons), the `#chrome` block and its stylesheet are gone,
the `BOOT` object pins the state, the shell (desktop or mobile) and the opening hash, and the
`<title>`. The mobile shell is part of `mc.html` itself: `S.mobile` (set from `BOOT`, or from the
viewport when unpinned) adds the thumb bar and the sheet layout on top of the phone rules the
"phone 400px" preview already used, so the preview in `mc.html` shows the same design.

Every scenario is also reachable inside `mc.html` from **Scenarios** in the sidebar.
The published artifact links below are the hand-drawn originals, kept for history; the
originals themselves are in git before the commit that first regenerated the files.
W12 (a coverage audit) is still hand-written.

W13 was added after the W12 audit closed and carries capability the spec does not yet describe:
skills, which ship **off** in every new workspace, a `search_skills` that answers from the
workspace's config rather than the model's memory, and the interjection — Oxagen stopping the loop
and putting a question to a person through the agent when a run starts in a repository nobody has
bound. It is in `mc.html` as the **Skills** page (`#/a-intel/<ws>/skills`, five tabs), the
off-by-default gate, the interjected run (`pRun()` hands `run_01K6QW3D5N7TYBA2` to its own
three-pane renderer) and the `in-the-loop` scenario, so `w13-in-the-loop.html` is generated like
the rest; the hand-drawn original is in git before the commit that first regenerated it. It is not
in the spec yet; `docs/w13-in-the-loop-scenario.md` has the walk, the cut-downs, and what still
needs a decision.
