Summary

The design is sound and the joints are not. Tacho already has the right primitives: a hash chain per session, a signed bundle the hook can check offline, a WAL shipped at least once, and a gateway that meters at the wire. The failures sit where those parts meet. Chain position lives in two files that disagree after a crash. One serial queue carries every agent's hooks, OTel, transcript reads and git work. The same model call or tool call gets a different identity at each capture level, so subagent work is counted twice. Install, reassign and uninstall each have a path that leaves a harness pointing at a dead proxy.

At 100 agents on one machine the first things to break are the serial queue, the full-state persist every second, and a 64-socket upstream pool in the model proxy. The first thing customers would notice is the price: the rate card charged Opus 4.5 through 5.5 at three times their list price, which inflated every spend and waste figure the product sells on. That one is fixed in this run.

The fixes in this run are in one pull request against macanderson/oxagen, split by area into separate commits, each with tests. Defects that need a schema migration, a maintainer decision or a rig are left open with a proposed change, and are listed in the findings and the roadmap.

One capture contract

Every level should produce the same frame shape and the server should apply one set of rules to it. The run ledger already has the stricter rules; the recording path should adopt them.

  • Stream identity. Each frame is keyed by stream and sequence, carries its content hash, and is claimed at genesis with host, root, parent and agent key pinned. A re-sent sequence with the same hash is a no-op; a different hash is a recorded conflict, never an overwrite.
  • Fact identity. A model call carries call_key (vendor request id, then message or response id); a tool call carries tool_use_id on every level, including the MCP gateway's _meta and the GitHub proxy. The ledger that judges duplicates belongs to the session family, not the chain.
  • Source precedence. Observed (gateway) over reported (OTel) over reconstructed (transcript), decided per call rather than per session, so a session with some unrouted calls is still counted fully.
  • One projection. Session counters, spend counters and cost.run_totals derive from one model-call projection through one pricing function.

Order of failure

  1. The serial queue. Hooks, OTLP, spool replay, transcript drains, SubagentStop reads, inline bundle refreshes and git push reads share one promise chain. Past a 5 to 10 s wait, hooks time out, answer locally and spool, which feeds a longer replay into the next hook.
  2. The full-state persist. daemon.json serialises every session kept for 7 days with its ledgers and children, and fsyncs it every busy second. At a few thousand retained sessions this is hundreds of megabytes per tick.
  3. The upstream pool. Call 65 to a vendor waits for a stream to finish, and its timeout never arms.
  4. The shipper. Health reads parse every unshipped event on every request, so a backlog drains quadratically, one batch in flight per host.
  5. The server. Synchronous ClickHouse inserts per request, FINAL scans on a column outside the sort key, and one drain per host that already sits near the per-host rate limit.

Target design

Writer per session

Replace the global queue with ChainWriter.append(session, seal) under a per-session lock. Hooks, OTLP, proxy, inbox, tailer, detector and gateway all go through it, so 100 sessions progress in parallel and seal-now-write-later races disappear.

WAL as the only authority

Rebuild cursors from WAL tails on start. Keep soft state per session and only for live sessions. Group-commit fsync every 10 to 20 ms, ship only the fsynced prefix, and move to 64 MiB framed segments with a CRC per record.

Deadlines and admission

Each hook carries its deadline. Past it, answer from the cached bundle and mark the frame late. No network work on the answer path; bundle refresh is single-flight with backoff.

Backpressure

A disk budget with a soft limit that compacts shipped data and drops shipped bodies, and a hard limit that stops bodies and low-value frames and seals a buffer_full gap. Never drop a policy decision or an agent stop.

Shipper

Two to four requests in flight over disjoint sessions with round-robin fairness, gzip bodies, pace to the rate-limit headers, and quarantine only an event the server names.

Proof it holds

A load test of 100 sessions by 1,000 hooks asserting p99 hook latency under 500 ms and flat memory, plus kill-9, torn-line and ENOSPC tests at every write site.

Steering delivery

How a steering record reaches a running agent today and what the record keeps about it.

  1. Compile. The server reads active records with a pinned version, ranks must over should over may over info, keeps must and should, drops superseded lineages, and packs them into a 16,384-byte prefix with a manifest of every candidate and why it was cut (packages/handlers/src/lib/tacho-steering.ts, packages/steering-assembler).
  2. Sign. The prefix becomes the bundle's context.system; the manifest rides along to hosts that advertise it. The bundle etag changes when the content does.
  3. Reach the host. Every ingest response and command poll carries the etag, and the daemon refetches when it differs: 5 to 30 seconds for every host.
  4. Reach the agent. Only at SessionStart: the hook answers additionalContext with the prefix plus any queued operator steers and seals a steering.manifest frame. A running session never sees a record merged after it started; it picks it up at resume, clear or compaction.
  5. Operator steers. dispatch_command queues a steer per live session; the next ingest delivers it, and the next UserPromptSubmit injects it and seals command_applied.

What is recorded and shown

The chain keeps a digest of the delivered text on the start event, the manifest of records included and cut, and command_applied frames for steers. The Steering Delivery tab reads the newest manifest per session and reports included and cut counts per run. Nothing records the text itself, the record version, whether the harness truncated the text, or the freshness gate's verdict, and no page names which records a given run received or links to it.

Defects fixed or proposed: fit the prefix under the smallest harness cap and record delivered characters (T-01); never drain steers on a replayed hook (T-02); fail steers to harnesses with no text channel (T-03); report interrupt as next step until the proxy injects (T-04); expire queued steers when a session ends (T-05); count bundle versions by etag (T-06).

Surfacing to add

  • A steering panel on the Run page: records received, records cut and why, and whether the session runs on an older text than the workspace's current one.
  • A Fleet view of live sessions still on an older steering text digest, with a one-click steer to reload.
  • Record reach per steering record: sessions that received version N since activation, from the manifests already in ClickHouse.
  • Mid-session channels that exist today: PostToolUse additionalContext for Claude Code, Codex and Cursor, and a Stop block with the steer as the reason for headless runs.

Session enrichment

Using the in-app Stella agent to name, summarise and read outputs, repositories and PRs from each session.

Today one job does this: every 5 minutes it re-reads every retained body of every changed run, map-reduces it on the Stella engine with no tools and no budget, and writes a name and a summary. It runs on live sessions from scratch each time (E-01). The fix in this run gates live runs to once every 30 minutes; the design below replaces the job.

Triggers

  • A run/sealed event at agent stop, deduplicated on the chain head hash and the prompt version
  • Live runs: the derived title only, plus an opt-in live account at most every 30 minutes when retained text grew by a fifth
  • Manual, with force; backfill priced before it runs

Inputs in two tiers

  • Always: the session row, files with line counts, commands, checkouts and remotes, PR and push frames, policy denials, the steering manifest, PR titles from GitHub. This alone gives repos, PRs, outputs and a good title.
  • Opt-in, retention permitting: redacted retained bodies after a server-side secret scan

Engine use

  • One stella-serve session per job with a fixed system prompt so map steps share a cached prefix
  • One declared tool, submit_run_account, with an output schema
  • Two steps at most and an enforced per-run budget

Outputs

  • Name, summary, goal, outcome claim, outputs, repositories, PRs, unresolved items and evidence gaps
  • Every claim cites frame sequence numbers; a validator drops claims whose frames are missing or of the wrong kind
  • PR and repository claims must match a receipt or a GitHub lookup

Idempotency and cost

  • A run_enrichments table unique on run, kind, input digest, prompt version and model
  • Chunk results memoised by digest, so a grown transcript pays only for new chunks
  • A monthly cap per org and a cap per run; sessions under three turns get the derived title only

Where it shows

  • Run header: name and summary marked generated, with model and time
  • Outputs and Work: derived items merged with recorded ones and linked to their frames
  • Fleet: name, then title, then id

Method

Ten reviewers read the code line by line in parallel, one area each: the hook path, the collector daemon, the WAL and spool, the recorder, the gateway, the CLI and install lifecycle, the desktop app, server ingest, the Fleet and Run pages with coaching, and steering with enrichment. Each finding was checked against the code before it was listed, and against open PR #3822 before it was fixed. Two findings were replayed on the recorded Claude Code 2.1.263 fixture (R-01, R-02), two were reproduced in scratch scripts (C-01, G-01), and the Claude Code hook behaviours behind R-04, R-07 and T-01 were checked against its current documentation.

Every changed behaviour has a test that fails without its fix, and each area's test files were run one file at a time and pass, across tacho, handlers, billing, telemetry, inngest-functions, the app and the desktop app. The desktop shell's 64 Rust tests ran against stub system libraries, since webkit2gtk is not installed here. The server command-delivery and rollup fixes also ran against a real Postgres 16 with every migration applied. Biome and eslint are clean on every changed file, and the fixes that touch files #3822 also changes were checked with a three-way merge against it.

Not verified here: behaviour on real Windows and macOS hosts (I-04 to I-08, D-02, D-03, D-07, D-10), Codex's real header names (G-03), Cursor payloads, and the full CI suites, which run on the pull request.
