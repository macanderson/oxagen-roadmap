# Mission Control, soup to nuts

This tour follows Mission Control in the order a new user meets it (sign-up, the onboarding gate, the first run) and then in the order an operator works in it every day (Fleet, a run, the agents and their tools, steering, money, the organization). Each section says what the user does on a page and why, in a few sentences, and ends with its sources: the audit prompt and the demo prompt that produced the screen, the spec section that governs it, the plan section that builds it, and the mockup page with its hand-written page spec. The page specs in `mockups/pages/` and the documents in `docs/` hold the detail; this file links to them and does not repeat them. Every screen uses the same demo record: Anderson Intelligence Corp. (`a-intel`), workspace `core-platform`, operator Marcus Bell. The full design is [`mockups/missioncontrol.html`](../mockups/missioncontrol.html), the product build is [`?product=1`](../mockups/missioncontrol.html?product=1&state=loaded&mobile=0) (phone: [`&mobile=1`](../mockups/missioncontrol.html?product=1&state=loaded&mobile=1)), and [`mockups/catalog.mjs`](../mockups/catalog.mjs) maps every page in every state.

Scope decisions made after 2026-09-14 (the Ontology cut, Audit moved out of the first release, witness first, GAU billing) come from [the scope review](scope-review.md) and the spec's amendments, and `missioncontrol.html` still shows some screens that will not ship in that release (Audit, per-run Billing, Run › Context), as recorded in [the scale-back prompt](scale-back-prompt.md).

## Part 1. First contact

### 1. Sign up

A new operator creates an account with SSO or with an email and password. The screen is the first of the sixty-seconds-to-governed path: sign up, verify the email, name the organization, wrap an agent, start a run. Submitting goes to email verification; SSO skips it and goes straight to naming the organization. Sign-in flows are not counted among the pages in the spec; they stay as the auth screens they are today.

Scenario: `sixty-seconds-to-governed` starts here ([W1](../mockups/missioncontrol.html#/a-intel/core-platform/scenarios/sixty-seconds-to-governed/1)), and walks sign-up through the onboarding gate to the first run on Fleet.

### 6. Name the organization

The first of three gate steps after sign-up names the organization and its first workspace. The organization is the tenant: it owns its own encryption key, billing account, retention policy and the namespace inside every agent key. Continuing provisions the tenant and moves to wrapping an agent. Mission Control stays locked until a first frame arrives, which is why these steps are a gate and have no app shell around them.

### 7. Wrap the first agent

The second gate step wraps the organization's first agent, and it is the same screen as step 2 of Register Agent with a different rail and Cancel target. The operator picks Claude Code, Codex or an SDK agent; wrapping installs the hooks and the `tachod` daemon, which puts the agent on the `harness` tier: steering is delivered and four hook events can refuse, client-attested and fail-open. The model proxy and the MCP aggregator that earn the `gateway` tier arrive with Phase 4 of the refactor path (spec §7.1, §17.2) and are not built yet. Nothing is pasted: the installer download carries the one-time enrollment token.

### 8. Start the first run

The third gate step waits for the first frame, showing a live log and an auto-open countdown. Mission Control opens the moment that frame reaches Oxagen and lands the operator on Fleet looking at their own run. The installer reports the git remote it saw, and the operator either binds that repository as the workspace's main repo (one click, which installs the GitHub App) or skips and leaves the workspace provisional for a stated number of days; Fleet's provisional banner reverses the skip.

### 9. The installer

The signed installer package renders its own three screens: download (package, size, signature, checksum, token), install (what it writes: the collector and the hooks today, and the base URL once the gateway's loopback proxy ships in Phase 4) and connected, with the uninstall command beside it. ## Part 2. The daily loop

### 10. The shell around every page

Once unlocked, every page sits in one shell: a sidebar with organization and workspace switchers, the Workspace nav (Fleet, Agent IAM, Tools, Steering, Spend; Skills moved under Steering on 2026-09-18) and the Organization nav (Organization, Billing, Audit); a top bar with breadcrumbs, ⌘K search-or-run and notifications; and an Account dialog from the user menu. On a phone the sidebar becomes a five-slot thumb bar (Fleet, Agents, Tools, Spend, More) with dialogs as bottom sheets. The in-app agent sits in the shell too, in scope for the first release (maintainer decisions, 2026-09-14 and 2026-09-15); each of its turns is a run of its own, acting through the same governed actions as the screens. It opens as a flyout from the sidebar, and the bottom dock of the `small-approvals-bottom-dock-scenarios` branch is not adopted (maintainer decision, 2026-09-15).

Scenario: `the-account` ([W11](../mockups/missioncontrol.html#/a-intel/core-platform/scenarios/the-account/1)) opens on Fleet and walks the Account dialog: how the operator signs in, preferences as governed actions, notifications, and the command menu as `search_tools`.

### 11. Fleet

Fleet is the workspace's home: every run, live and recent, with its enforcement tier (one of four words, observe, harness, gateway, contained, computed from what was actually routed; every wrapped run reads `harness` until Phase 4), replay grade, verdict, cost so far and frames, and the approvals queue as a panel beside them, because an approval is always about a run. Agents start runs; on Fleet an operator pauses, resumes, cancels, steers one run or the whole fleet, or opens a run. An approval card shows the four-hop chain (who asked, which agent, which action, which rule) and a live countdown; approving mints a single-use token bound to that exact call, and a timed-out approval never dispatches. When a run is stopped on an interjection, a banner above the tiles offers **Answer it**.

Scenarios: `stop-it-steer-it` starts here ([W2](../mockups/missioncontrol.html#/a-intel/core-platform/scenarios/stop-it-steer-it/1)), pausing and steering a live release run; `money-asked` starts here in the `finops` workspace ([W3](../mockups/missioncontrol.html#/a-intel/finops/scenarios/money-asked/1)), a payment above its mandate parked for a human.

### 12. Run

Opening a run gives a frame-by-frame player: the transcript at three zoom levels under a transport (scrub, step, play, pause, speed), the approvals strip for this run, and tabs for governed actions, proof, cost, policy, context and chain and seal. The header carries pause, steer, cancel and export; the chain tab offers fork replay from a frame and bisect against another run. Every trust badge shows the recorded value and nothing stronger, every money figure shows its basis, and every explanation is a chain of links to frames, records and commits. The Context tab is one of the screens the first release does not ship.

### 13. A run stopped on an interjection

A run that starts in a repository no workspace owns, with skills on, has a config to resolve and nothing to resolve it against, so Oxagen stops the loop before the first model call and puts the question to a person through the agent. The same route renders this page in place of the ordinary player, showing the moment from three sides: the agent's own window, Oxagen's card with the two paths (link the repository to an existing workspace, or create a new one) and their consequences, and the frame strip with the frames still to come greyed out. Either answer is a governed action, and an unanswered interjection times out to `deny` at thirty minutes. The spec does not describe interjection yet; the W13 scenario doc carries it.

### 14. Agents

The Agents list (Agent IAM in the nav) holds every agent identity in the workspace. Identity lives in Postgres and the definition lives in git, joined by the agent key and the definition digest. From here an operator registers, enrolls, assigns roles and deregisters. Registering opens a Context PR that adds `.oxagen/agents/<slug>.toml`, and deregistering retires the principal so its runs keep their identity.

### 15. One agent

An agent's page answers what it is and what it may reach: its principal and run credential, roles and delegation ceiling, the toolbelt exactly as the model receives it with per-tool decision rules, its mandates, budgets and token accounting, runs, enrollment on the host, tamper incidents, and its definition in git. The belt is computed at run start from grants and policy, and a searchable belt shows the `search_tools` view. Rotating the credential or suspending the agent kills every live run token at the next call, and both land in the audit record.

### 16. The agent's source

The agent's definition file, `.oxagen/agents/<slug>.toml`, opens in a source editor. ### 17. A mandate

A mandate is delegated financial authority an agent holds. Its page shows the per-call and per-period limits, what has been settled and reserved against it, the grant that created it, and the reconciliation of every draw to a receipt. Amounts are reserved at decision time and settled on the receipt, so settled, reserved and remaining always add up to the period limit. A financial tool whose schema exposes no amount cannot hold a mandate, and changing limits needs a second approver.

### 18. Tools

Tools governs everything an agent can call: the registry of servers, tool versions, schemas and safety classification; connections and their owners with credential grants; the mandates ledger; policy versions with tests and simulation; kill switches with their blast radius; auto-approval rules; and the last assurance result. A tool is `name@schema-version` everywhere it appears. Policy is deterministic and versioned, a draft is simulated against real history before activation, and every kill-switch flip records who, when and why. The first release keeps the registry, connections, mandates ledger, policy, kill switches and auto-approvals, and leaves out the assurance suite, policy simulation and two-person mandates.

### 19. Skills

Skills is a tab of Steering (section 20), the second of seven, at `/{org}/{ws}/steering/skills`. It has no navigation entry of its own since 2026-09-18, and an old `/skills` link is rewritten in place. A skill is steering, and it is a file: governed through a pull request like a record, delivered to the harness by sync, and its description line competes in the assembler like any other item (spec §10.6).

Every new workspace ships with skills off, and the off page says so: `skills.enabled = false` is the value the workspace was created with. It states what turning skills on does (adds `search_skills` to every belt, prices skill loads, starts skill frames, governs `.oxagen/skills.toml`) and what it does not, and turning it on is a pull request against the main repo. Once on, the Skills tab governs resolution; the harness runs a skill, and Oxagen decides which skills the workspace config lets an agent find and load, what that cost, and what was held back and why. Its views cover the catalog, a `search_skills` console answered as the gateway would answer it in a run, the seat in the loop (interjection and quarantined reflection), and the config's history as pull requests.

Scenario: `in-the-loop` starts here ([W13](../mockups/missioncontrol.html#/a-intel/core-platform/scenarios/in-the-loop/1)); the walk, its cut-downs and the open decisions are in [the W13 scenario doc](w13-in-the-loop-scenario.md).

### 20. Steering

Steering is the hub for everything that can steer an agent, and it is how agents learn under review. Its tabs, in this order: **Records** (published context records), **Skills** (section 19), **Memory** (what agents remembered, with the frame that taught it), **Ontology** (a small home for ontology notes that steer; the ontology engine stays cut), **Policy** (gates, each with the one-line gate notice it emits into steering), **Proposals** (candidates and open Context PRs with their checks, which steer nothing until merged) and **Preview**. Preview is the page that makes the competition visible: pick an agent and a prompt, and see exactly what would be injected, what was cut, and why. All of it competes in one assembler, and what it rendered and cut is a `steering.manifest` frame on every run (spec §10.5, §10.7). A record is published by merging its pull request on GitHub; saving on this page publishes nothing. Checks hold records to `require` or `forbid`, so a record can never grant authority. Effect metrics and retirement candidates stay out. The mockups depict the hub complete (Phase 2 of the refactor path, spec §17.2). In the product today the page lists records, proposals and Context PRs, and no published record reaches a wrapped agent yet: that is Phase 0. The `gateway` and `contained` tiers appear on the ladder as tiers not yet available, and no screen claims a model proxy, observed metering, an enforced budget, a real interrupt or a sandbox as present.

Scenario: `learned-approved-changed` starts here on Records ([W6](../mockups/missioncontrol.html#/a-intel/core-platform/scenarios/learned-approved-changed/1)), from a learned rule to a merged pull request to the next model call carrying it.

### 23. Billing

Billing is readable by a finance role and shows the plan, this period's lines, the meters and the invoices, with a row opening the Stripe-hosted invoice and Change plan going to Stripe checkout. Billing charges on two meters ([spec §12.1](mission-control-spec.md#121-what-is-tracked-and-what-is-priced); 2026-09-15, maintainer decision). Governed actions are priced in governed action units on one price list (maintainer decisions of 2026-09-14, reaffirmed 2026-09-15): $5 per 1,000 GAU list, a monthly allowance of 5,000 GAU on Free, 50,000 on Build at $199 and 300,000 on Scale at $999, 5,000-GAU blocks at $25, and Enterprise negotiated per contract, with every feature on every tier. The page prints the customer's contracted rate, and `resolve_approval` is the only billable governed action. In-app AI usage, the in-app agent's model calls, is priced in usage credits: 1 credit = $0.01, debited at provider cost times the meter markup, funded by the $5 signup grant and topped up with credit packs. Tokens are not passed through at cost. Proven spend is a report figure. The mockup still prints the proven-run price list, which the spec no longer carries. The customer-spend accounting on Spend is unchanged. The billing decisions of 2026-09-15 (the two meters, credit packs for usage credits, negotiated enterprise with every feature on for every tier, invoice billing, the Build and Scale upgrade through Stripe Checkout, suspension) are in [spec §12.10](mission-control-spec.md#1210-billing-decisions-of-2026-09-15).

### 25. Register another agent

Every later agent arrives through Register Agent, opened from Fleet, which reuses the onboarding gate's wrap and first-frame components in three steps.
