The shift

The current agent can inspect executions, memory and ontology relationships. The next agent should be a permissioned work copilot: it can retrieve current workspace evidence, calculate and visualize, produce durable artifacts, and stage or apply changes with explicit consent.

01 / UNDERSTAND

Read the workspace

Tasks, repos, docs, designs, decisions, incidents, metrics, people and prior agent work.

02 / MAKE SENSE

Explain the evidence

Compare, calculate, map dependencies, show assumptions and cite the records behind claims.

03 / MAKE

Produce artifacts

Charts, graphs, briefs, reports, PDFs, HTML, data exports and eventually slide decks.

04 / ACT

Take approved action

Prepare diffs, ask for consent, execute through policy, verify the result and leave a receipt.

Design principle: the agent should use the app's identity, entitlement, consent, provenance and audit controls—not create a parallel authorization system.

From ontology to Workspace Context

“Ontology” is still useful as an internal schema and governance layer, but it is no longer the right user-facing concept. People want to understand work, not traverse a graph schema.

Existing ontology tools can remain stable aliases during migration. New APIs and product copy should say Context entity, Explore relationships and Evidence link.

Phased roadmap

Use the filters to focus the roadmap. Each phase has an outcome, deliverables and an exit condition.

PHASE 0

Contract and foundation

Define Workspace Context vocabulary, provenance, tool annotations, consent classes, receipts and artifact metadata.

  • Ontology-to-Context compatibility aliases
  • Scope, side-effect, egress, idempotency and reversibility schema
  • Fixtures for citations, refusals, stale data and filtered results
Exit: every new tool declares risk + provenance
PHASE 1

Read parity and workspace understanding

Let the agent inspect the same read surfaces people rely on to understand work.

  • App surface discovery and workspace search
  • Context entity resolution and relationship exploration
  • Source spans, citations, freshness and partial-result indicators
Exit: five representative management questions answered from current evidence
PHASE 2

Analysis and visual intelligence

Turn workspace data into trustworthy calculations and inspectable visuals.

  • Reusable metric definitions and bounded analysis runtime
  • Charts, tables, timelines, matrices and relationship graphs
  • Deterministic specs, exportable SVG/PNG/HTML and accessible fallbacks
Exit: users can inspect how throughput, aging and dependency risk were calculated
PHASE 3

Artifact studio

Make analysis durable, reviewable and ready for an audience.

  • Versioning, preview, diff and validation
  • HTML, Markdown, PDF, CSV, JSON, SVG and PNG
  • Templates for staff updates, leadership briefs, board memos and incident reviews
Exit: a cited leadership brief can be generated, reviewed and regenerated
PHASE 4

Governed app actions

Let the agent prepare and apply changes a user can make in the app.

  • Action-plan drafting and exact diffs
  • Create, edit, link, assign and status operations
  • Approval UI, idempotent adapters, receipts and verification
Exit: approval applies exactly the reviewed plan
PHASE 5

Distribution and operating loops

Deliver approved work where teams already operate.

  • Approved repositories, drives, docs, presentations, chat and email
  • Board packets, leadership presentations and refreshable reports
  • Audience checks, delivery receipts and revoke/unpublish where supported
Exit: a board packet is generated, approved, distributed and traced end to end

Guardrails and artifact quality

Every mutation follows intent → affected resources → proposed diff → policy check → consent → execution → receipt → verification. Read and draft operations can be fast; consequential changes and external distribution need a named approval boundary.

visualization = { kind, title, data: { query, snapshot, rows }, encoding, filters, assumptions, provenance, accessibility } artifact = { id, type, version, content, sourceRefs, renderRecipe, audience, state, digest } actionPlan = { intent, affectedResources, diff, policyResult, consent, requestId, receipt, verification }
C0 readC1 draftC2 reversible changeC3 consequentialC4 high-impact

Charts and graphs must render deterministically from a stored spec and snapshot, include accessible table/text fallbacks, disclose stale or partial data, and preserve the evidence behind every material claim.

Recommended next move

Approve Phase 0 plus the Delivery health brief slice. It exercises the complete future loop—retrieve current work, calculate a defined metric, render a chart, create a cited HTML artifact—while leaving external distribution and mutations behind explicit later approvals.
