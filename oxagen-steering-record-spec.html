Specification

Steering records

A steering record is one piece of guidance an agent runs under: a business rule, a code rule, a constraint, a procedure, a skill, a fact, a style preference, or a memory. Each one is a Markdown file with YAML frontmatter in the repository, published through a steering PR, and delivered to every agent the workspace governs.

Decisions

Decision status

Decided

  • The name is steering record, and the pull request that publishes one is a steering PR. No older name remains in the product, the code, the schema, the API, or the MCP tools.
  • A steering record is a Markdown file with YAML frontmatter, with the .md extension.
  • The kinds include business rules, code rules, style preferences, facts, skills, and memories, alongside the kinds in use today. There is no agent persona.
  • The section of the app that holds them is Steering.

Today

  • One published record per lineage, in the repository, published only by a merged pull request.
  • Four forces (must, should, may, info) and a constraint's effect of require or forbid. A record never grants authority.
  • The id and hash come from the content, by the two-pass hash, and the label stays outside the hash (ADR-178).
  • Six checks on every steering PR, and review by the workspace's governance mode.

Proposed

  • The directory .oxagen/steering/, one record per file, named for its lineage.
  • Flat field names: lineage, scope, force, effect.
  • The rule kind splits into business-rule and code-rule.
  • applies_to and load, so a record can target paths and load on match, relevance, or mention.
  • @path and @record references in the body, resolved when the record is delivered.
Layout

File locations

Workspace records live in the workspace's main repository and steer every run in the workspace. Repository records live in a linked repository and steer only runs on it. A repository record may narrow what a workspace record allows. It may never widen it. Today

The directory name is Proposed. It replaces .oxagen/rules/. A file's name is its lineage plus .md, so renaming a file is never how a record changes.

Anatomy

Parts of a file

  1. Opening fence. The file starts with --- on its own line. Nothing comes before it, not even a blank line or a byte-order mark.
  2. Frontmatter. YAML, from a strict subset: plain mappings, lists, and quoted or plain strings. No anchors, aliases, tags, or multi-document streams.
  3. Closing fence. A second --- on its own line ends the frontmatter.
  4. Body. CommonMark. It is the record's statement, the text the agent reads. It may hold headings, lists, and fenced code.
  5. References. @packages/database/src/tenancy.ts names a file in the repository. Proposed

Style preference

Constraint

Memory

Memories live in Oxagen, where every agent's memories are gathered, in the same format. The cloud gateway adds the recalled ones to a turn. A memory reaches the repository as a file only when a steering PR promotes it. Its provenance points at the frame that taught it.

Body

The statement

  • The body is CommonMark and must hold at least one line of text. An empty body fails the schema check.
  • Write it to the agent, in the second person or the imperative: "Ask in the run and wait."
  • Fenced code blocks show the pattern to follow. Use the language tag of the code.
  • Keep one idea per record. Two ideas are two lineages, so each can be revised and retired on its own.
  • Proposed @path/to/file names a repository file, and @record:acme.platform.no-push-to-main names another record. The cloud gateway resolves both when it delivers the record, and the record's manifest entry lists what it pulled in.
Identity

Id and hash

A record's identity comes from what it says, never from the file's bytes. Reformatting a file, reordering its fields, or renaming its label leaves the hash unchanged. The hash is SHA-256 over RFC 8785 canonical JSON, with null members stripped, as Stella and the protocol compute it today. Today

  1. Preimage. Parse the frontmatter. Drop id, hash, and label. Add the body as statement, with line endings as \n and trailing newlines removed.
  2. Pass 1. Hash the preimage. The first 12 hex characters, after rec_ and the lineage slug, make the id.
  3. Pass 2. Hash the preimage again with the id in it. That is the hash.

The body normalization in step 1 is Proposed: the v0.1 format stored the statement as a TOML string, so it never needed one.

Skills

Skill records

A skill is a steering record whose file is SKILL.md inside a folder named for the skill. The folder may hold the files the skill refers to. The frontmatter adds name and description, the two fields harnesses read, so a steering PR can place the folder where each harness looks for skills. Proposed shape

Steering PR

Publishing

Nothing steers until a steering PR merges. The registry keeps every version, and the merged file decides what is in force. Today

  1. Open. A person, the promoter, or an agent's proposal opens a branch steering/<lineage> with one record file and a pull request. The body carries the rationale and the evidence. One record per pull request.
  2. Check. Six checks run: schema, lineage uniqueness, hash recomputation, a secret and personal-data scan, conflicts with active records, and the authority rule. See Validation.
  3. Review. By governance mode: in solo the author may merge, in team a code owner approves, in regulated a named approver from a role approves.
  4. Merge. Oxagen writes id and hash, appends a row to promotions.jsonl, records a promotion event, and publishes the record.
  5. Retire. Another steering PR sets status: archived. The file stays.

The branch prefix steering/ is Proposed, replacing the prefix the old name used.

Cursor output

Cursor ignores a plain .md file in .cursor/rules/, so the steering PR writes an .mdc file there, mapping label to description, applies_to to globs, and load: always to alwaysApply: true. The comment on the last line ties the file back to its record. Proposed

Validation

Check failures

YAML reads some bare words as other types: no and off become false, and 2026-09-25 becomes a date. The schema check validates the parsed values against the JSON Schema below, so a value of the wrong type fails instead of slipping through. Quote any string that could be read another way.

Migration

Migration from v0.1

Today each record is a TOML file under .oxagen/rules/. One steering PR per repository converts every file. Readers accept both formats until that PR merges, then the TOML reader is removed. With no customers yet, the conversion is one pass per workspace.

v0.1 TOMLv1 frontmatter
schemaschema: steering-record/v1
set_id (per file)Dropped. The repository's workspace binding names the set
lineage_idlineage
record_id, record_hashid, hash, recomputed over the new preimage
kind = "rule"business-rule or code-rule
statementThe body
sharing_scopescope
[record.provenance] source_kind, source_uriprovenance.source, provenance.uri
[record.steering] forceforce

Converting a record changes its preimage, so its id and hash change once. The conversion PR records each old id beside its new one in promotions.jsonl, so every run that cited the old id still resolves.

Open questions

Open questions

  1. Kind names: business-rule and code-rule as two kinds, or one rule kind with a domain field.
  2. Lineage prefix: today's lineages start with ctx.. Drop it and use <set>.<slug>, as the examples here do.
  3. The applies_to and load fields, and the @path and @record references.
  4. Where memories live as files: every memory in the repository, or only the ones a steering PR promotes, with the rest kept in Oxagen.
  5. What Codex receives as files, beside what the cloud gateway adds to its model calls.
